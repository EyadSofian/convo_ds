# CONVO — ابدأ من هنا

هذه حزمة prompt تنفيذي لبناء منصة إدارة محادثات وقنوات وحملات، تدعم **SaaS لشركات متعددة وSelf-hosted لشركة واحدة**، بنفس الكود والعقود والصلاحيات. الحزمة تطور البحث والـprompt السابقين؛ لم نعدّل الملفات الأصلية.

## الملفات

| الملف | استخدامه |
|---|---|
| [MASTER-PROMPT.md](MASTER-PROMPT.md) | الـprompt الكامل المستقل: product/business logic، frontend/backend/APIs، Meta، Figma، roles، campaigns، tests، deployment |
| [PHASE-PROMPTS.md](PHASE-PROMPTS.md) | بطاقات تنفيذ P0–P9، تعليمات مشتركة، استئناف العمل وقالب أدلة المهمة |
| [RESEARCH-UPDATE.ar.md](RESEARCH-UPDATE.ar.md) | المصادر التي تحققنا منها، أسباب القرارات، ما تغيّر وحدود التحقق |
| [REVIEW.md](REVIEW.md) | مراجعة اتساق المواصفات وقابلية فهمها؛ ليست نتائج اختبارات التطبيق |

## رسالة البداية للـagent

أرفق MASTER-PROMPT.md وPHASE-PROMPTS.md داخل مستودع التطبيق، ثم استخدم:

```text
اقرأ MASTER-PROMPT.md كاملًا، ثم تعليمات التشغيل المشتركة وبطاقة P0 في
PHASE-PROMPTS.md. نفّذ بناء CONVO وفقهما، مع دعم SaaS وSelf-hosted معًا.
ابدأ بفحص الكود الموجود، ثم حوّل المتطلبات إلى سجل قابل للتتبع، وانتقل للتنفيذ
في مهام صغيرة مكتملة frontend/backend/API/tests. حافظ على العمل الموجود.
لا تعتبر شاشة أو endpoint مكتملًا من غير تحقق سلوكي وأدلة مرتبطة بالمتطلبات.
لا تختلق نجاح Meta أو الاختبارات أو النشر. استمر في العمل المستقل عند غياب
اعتماد خارجي، واطلب فقط المعلومة التي تمنع الخطوة المرتبطة به.
حدّث docs/execution/current-task.md بعد كل مهمة، وأكمل المراحل المطلوبة.
```

لو ستستخدم chat لا يستطيع قراءة الملفات، الصق الـmaster كاملًا في البداية، ثم بطاقة المرحلة الحالية. إذا كانت سعة السياق محدودة، أرسل الأقسام على دفعات مرقمة واجعل الـagent يسجل ما قرأه قبل التنفيذ. لا ترسل بطاقة المرحلة وحدها وتفترض أنها تحتوي كل قواعد النظام.

الأسماء والمسارات داخل البطاقات أهداف ينشئها الـagent أثناء التنفيذ. لا تعني أن OpenAPI أو التطبيق أو تقارير الحمل موجودة بالفعل. التعليمات التقنية بالإنجليزية لتثبيت أسماء العقود والكود، بينما ملخص البحث وطريقة الاستخدام بالعربية.

## النطاق والترتيب

| المرحلة | الناتج المطلوب |
|---|---|
| P0 | فحص المشروع، بحث موثق، business rules، ERD/APIs، Figma design handoff وخطة اختبارات |
| P1 | أساس المشروع ونسختا التشغيل، users/roles/teams/tenancy/auth والصلاحيات |
| P2 | WhatsApp ورسائل فعلية وInbox مترابط بالـbackend والـrealtime |
| P3 | Messenger وInstagram والقوالب وجهات الاتصال والاستيراد والتعاون |
| P4 | Broadcasts: جمهور وموافقات وجدولة وحدود وإرسال وتتبع وإيقاف ومصالحة |
| P5 | Public API/SDK/webhooks وتكامل Odoo الموروث من المواصفات السابقة |
| P6 | التوجيه، SLA، automation، التقارير والاستهلاك |
| P7 | AI وRAG والأدوات وتسليم المحادثة للموظف، بعد ثبات نواة الرسائل |
| P8 | اختبارات الإطلاق والأمان والنسخ والاستعادة ونشر SaaS وSelf-hosted |
| P9 | سجل إضافات صريح للقنوات والقدرات الأخرى؛ تُنفذ عند تحديد أولويتها |

«كل كود يتختبر» تحول إلى تغطية سلوك، عقود API، صلاحيات، اختبارات تكامل وE2E، حالات فشل وتزامن، مراجعة مرئية واختبارات نشر واستعادة، مع أهداف coverage صارمة. هذه بوابات تحقق، وليست وعدًا أن 100% coverage تعني صفر bugs.

## المطلوب أثناء التنفيذ الفعلي

لا تحتاج هذه المعلومات لاستخدام الـprompt أو بدء البرمجة. يحتاجها المنفّذ عند المرحلة المعنية: مستودع التطبيق، أصول Meta والتصاريح وبيانات اختبار مصرح بها، النطاق/السيرفر/المنطقة، حجم الاستخدام الفعلي، إعداد البريد، وإصدار Odoo وحسابه إن كان سيتم تشغيل التكامل. تُدخل الأسرار في مخزنها أو بيئتها الآمنة، لا في نص الـprompt.

الحزمة تتطلب إكمال كل العمل المستقل وعدم تعطيله بسبب حساب خارجي مفقود، مع بقاء live verification والنشر غير مكتملين حتى تقديم دليل فعلي.
