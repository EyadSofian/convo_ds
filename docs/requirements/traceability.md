## How to read this registry

Four **independent** status fields. None is derived from another.

| Field | Allowed values |
|---|---|
| `Impl` | `planned` / `partial` / `implemented` |
| `Test` | `not_run` / `failing` / `passed` / `blocked_env` |
| `Live` | `n/a` / `blocked_no_asset` / `simulated_only` / `provider_live_verified` |
| `Dep` | `n/a` / `not_deployed` / `staging_verified` / `production_verified` |

Rules enforced on this file:

- A test command that was never executed is `not_run`. It is never `passed`.
- A provider simulator passing is `simulated_only`. It is never `provider_live_verified`.
- A missing external credential blocks only the `Live` column. It never lets `Impl` or `Test` be skipped.
- Every row must eventually name its migration/route/component/test path in `Evidence`.
- No row is deleted to make the registry look complete. Descoped rows move to `descoped` with an ADR link.

At P0 close, every row below was `Impl=planned`, `Test=not_run` — that was the honest baseline, not a gap to hide.

**P1-T5 / Milestone B, first slice (2026-09-09)** delivered the role boundary: the matrix, the engine, and the administration read surface.

`packages/domain/src/iam/` is new and framework-independent. `permissions.ts` mirrors the 29-key catalogue and the non-delegable set, with tests that parse `0003_permission_catalogue.sql` so the module and the database cannot disagree. `roles.ts` holds the seven built-in roles as data, transcribed cell by cell from `business-rules.md` §7 — and `roles.test.ts` asserts every cell *and* parses `0007_role_matrix.sql`, so the matrix exists in exactly one place with two mechanical checks around it. Platform Super Admin is deliberately not among them: it sits outside tenant membership, and modelling it as an eighth role would put it inside the boundary the rules forbid.

`authorize.ts` implements invariant I3 as five sequential narrowing terms — active membership ∩ tenant status ∩ action grant ∩ delegation ceiling ∩ resource scope. There is no branch that widens a decision, which is what makes default-deny structural rather than aspirational, and a `Principal` carries grants rather than a role label, so there is nowhere to write `if (role === 'admin')`. 41 tests cover each term in isolation, `own` reached by assignment and by past participation, lost inbox access overriding assignment, an empty ceiling meaning "nothing" rather than "no ceiling", and a full 7-role × 29-key sweep.

One design defect was found by a test and fixed rather than accommodated: the denial reason was originally derived from the grant *level*, so an agent who had lost inbox access was reported as `not_own_resource`. The reason now names the term that actually failed, because the operator's next step and the audit line differ between "ask for the inbox back" and "this is not your conversation".

Migration `0007_role_matrix.sql` adds `scope_level` to `role_permissions` — until now a grant carried no scope and every grant behaved as tenant-wide — seeds all seven roles per tenant, and adds `memberships_keep_an_owner`, a **DEFERRABLE INITIALLY DEFERRED** constraint trigger. Last-Owner protection lives in the database because two concurrent transactions each removing "the other" Owner would both pass an application-level check; deferring it to commit is what lets a legitimate transactional transfer be Owner-less mid-flight and still commit with exactly one Owner. `none` is deliberately absent from the `scope_level` CHECK: a denial is the absence of a row, and two representations of denial is how a permission check ends up reading the wrong one.

`apps/api/src/authorization/authorization.service.ts` is now the single HTTP entry point to the engine. It loads the principal **inside the same RLS transaction the work runs in**, so a membership revoked between check and write cannot be used. Before this, `PermissionService` inlined `SELECT ... WHERE permission_key = 'role.manage'` — correct for one route, and the beginning of a per-endpoint copy of the rules. Non-membership, revoked membership and an inactive tenant all conceal as 404; 403 is reserved for "you are a member here and this action is denied", because answering 403 to a stranger confirms the company exists.

Three routes were added and documented: `GET /tenants/{id}/roles`, `/people`, `/teams`. The bidirectional route/spec drift test passes with the pinned OpenAPI updated, and the contract now pins that `scope_level` admits only `tenant|scoped|own` so a client cannot render a "none" chip.

`tests/integration/api-authorization.test.ts` (16 tests, real PostgreSQL) proves the database half: all seven roles seeded with the scope levels the domain declares, every built-in role gated correctly across the administration surface, revoked membership concealed as 404, unknown and malformed tenants refused identically, the last-Owner trigger rejecting both revoke and demote, a transactional transfer succeeding, and — with a deliberately small pool — that a reused connection never carries one tenant's context into another transaction and that no context at all means zero rows.

**P1-T5 / Milestone B, second slice (2026-09-09)** closed IAM-03, password recovery.

`POST /auth/recovery` always answers 202 with the same body — known address, unknown address, rate-limited address alike. A 429 would confirm to an enumerator that they had found a real, rate-limited target, so the delay is applied through the shared limiter and never announced. A decoy challenge with a NULL user is written for an unknown address, so the table's shape and growth are not a directory of real accounts. `tests/integration/api-recovery.test.ts` asserts this by comparing the **entire response body byte for byte**, with the request id pinned, rather than by reading the code.

Only fingerprints reach PostgreSQL: the raw token lives long enough to hand to the delivery port and is never written, logged or returned, and the stored value is asserted to be a 64-hex HMAC. `POST /auth/recovery/complete` claims the challenge with a conditional UPDATE — two concurrent requests holding the same token cannot both win — then replaces the password, revokes **every** session for the account, and spends every other outstanding challenge, all in one transaction. Expired, already used and never issued return one answer, because all three mean "start again".

Delivery is an injectable port and it is **not wired**. `LoggingRecoveryDelivery` logs a redacted address, never the token, and deliberately does not throw, because a recovery request must look identical whether or not delivery is configured. It is not an email integration and must not be described as one; a provider and its credentials are open dependency #9. `createApiApplication` now takes an `adapters` argument, since the composition root is where an outbound integration is chosen.

One branch was **deleted rather than tested**: the first implementation handled a decoy token in `complete()` with its own path, which no request could reach because decoy tokens are never delivered. The requirement moved into the claiming predicate (`AND user_id IS NOT NULL`), so a guessed decoy is refused by the same path as an unknown token. Coverage found it; the fix was to remove the code, not to write a test that pretended to reach it.

Gates: lint / typecheck / build exit 0; `test:unit` 664; `test:integration` 15 files / **111 tests**; `test:coverage` 61 files / **775 tests** at 100% lines / statements / functions, 98.95% branches.

**P1-T5 / Milestone B, third slice (2026-09-09)** closed IAM-06, invitations, and restored the coverage gate to 100% on all four metrics.

Branch coverage had been sitting at 98.95% against a threshold of 95, so it could rot to 95 without failing. Twenty-two uncovered branch paths were resolved one at a time: six were deleted as unreachable (a non-nullable `ownerDocument` fallback, a finite-by-construction guard, an attribute re-read that `closestWithAttr` had already proved present, an optional parameter every caller passes, a campaign-example lookup whose fallback key cannot be missing, and a tab fallback the guard above it prevents), and the rest were covered with tests for behaviour that genuinely happens. The threshold is now 100.

Invitations store only an HMAC fingerprint. Creation requires `member.manage`, CSRF and an `Idempotency-Key`, and runs the authorization **inside the idempotency transaction** rather than opening a second one, so the record and the invitation commit together and a retry replays the first answer instead of minting a second live token. A second invitation for the same address supersedes the first, because two valid tokens for one seat are two ways in and revoking one would silently leave the other open; a partial unique index enforces the same thing if the code ever skips it.

The role and scopes are checked against the inviter's own grants by `canAssignRole` and `canGrantScopes`. An Admin cannot invite an Owner — not because of a rule naming "Owner", but because Admin does not hold `tenant.delete`. A scoped inviter cannot grant an inbox they cannot see themselves, or "scoped" would be a formality anyone could widen by inviting a colleague.

Acceptance is unauthenticated by necessity and needed one new primitive. `FORCE ROW LEVEL SECURITY` applies to the table owner too, so a `SECURITY DEFINER` lookup could not read the invitation either; the first attempt at one was removed. Instead `withCredentialResolvedTenant` sets a transaction-local credential fingerprint that the invitations policy admits **for exactly the row carrying that token** — one row wide, not a flag that opens the table — reads the tenant off that row under `FOR UPDATE`, and then enters the tenant's normal context for everything else. Writes are unaffected: `WITH CHECK` stays tenant-only.

Accept requires a password in both cases: it creates the identity when the address has no account and proves it when it does. Without that, holding the link would be enough to attach a stranger's established account to a company. Unknown, expired, revoked, already-used and wrong-password all return the same 400 — asserted byte for byte with the per-request id stripped — and a wrong password does not burn the invitation. A successful accept clears the attempt counter, so a company onboarding ten people from one office does not lock itself out while a guessing run, which never succeeds, keeps counting.

Two constraints did their job during development and were kept rather than loosened: `invitations_accepted_membership_ck` caught an ordering where the invitation was briefly "accepted by nobody" (fixed by taking the row lock first and setting status and membership together), and `tenants` RLS caught a test that tried to suspend a company from outside its own context.

A visual-regression flake introduced in Milestone A was fixed at the cause: the seeded dataset derives every timestamp from `new Date()` at boot, so baselines drifted with wall-clock time. Playwright's clock is now frozen before the bundle runs, and the 40 baselines were regenerated once against it.

**P1-T5 / Milestone B, fourth slice (2026-09-09)** delivered the People, Roles, Teams and ownership **mutation** surface, closing IAM-14, IAM-15 and IAM-16.

Twelve routes, all behind CSRF: change a membership's role, status or scopes; create, replace and delete a custom role; create, rename, archive a team and move people in and out of it; offer, accept, decline and cancel ownership. None carries an `Idempotency-Key`, because none of them duplicates an effect on replay — a repeated role change sets the same role. The one mutation that mints a credential, creating an invitation, does carry one.

Every grant-producing change is checked against the actor's own grants by the pure functions in `@convo/domain`, and the database backs the same rules where a service bug would otherwise be the only thing in the way. Migration 0009 makes built-in roles and their grants immutable — and the interesting part is *how*: a blanket refusal would also block the legitimate write, since every new company seeds its built-in roles at creation. The trigger instead admits exactly the rows that already exist in `builtin_role_grants`, which permits the seed, refuses an added key, a widened scope, an edit and a delete, **and** catches a seed that disagrees with the matrix. That is a stronger guarantee than "nothing may write here", and it was found by the bootstrap failing under the first, blunter version.

Ownership transfer is an offer the recipient accepts, not something an Owner does to somebody. Offering requires `tenant.delete`, the one key separating Owner from Admin, so "only an Owner may transfer ownership" is true without any code naming the role. Only the recipient may accept or decline and only the offerer may cancel; anyone else gets 404, because whether an offer is outstanding is not their business. Accepting demotes and promotes in one transaction — the company is genuinely Owner-less between the two updates, which is precisely why the last-Owner constraint is `DEFERRABLE INITIALLY DEFERRED`.

Teams are archived, not deleted, so their routing history and membership rows survive; a team name is reserved only while the team is live, so an archived name is reusable.

Every mutation writes an `admin_audit_events` row **in the same transaction as its effect**, so the record and the change cannot disagree. The runtime role has `SELECT, INSERT` on that table and nothing else, so an audit row cannot be edited or removed by the application at all.

**P1-T5 / Milestone B, fifth slice (2026-09-09)** wired the People, Roles and Teams screen to the API. It is the first screen in `apps/web` that talks to a server.

Nothing on it reads the demo dataset. The demo People screen was **deleted** rather than left beside the real one, because two implementations of one screen is how a demo gets shipped by accident. Every list is a four-state resource — not asked, waiting, refused, here it is — so "the server said no" and "there is nothing here" are different things on screen instead of collapsing into an empty table. A denial is rendered as a permission state that says the refusal happened on the server, because hiding a control is not an authorization control.

Every mutation follows one shape: mark the control busy and re-render, await the server, and only then record success and reload. No toast fires on click and nothing is written optimistically, so what is on screen after a change is what the server stored — including fields the browser never asked about. The rejection is shown beside the form that caused it, with the server's own message, its field details and its request id.

Three defects the wiring exposed, all fixed at the source rather than in the screen:

- Signing in resolved the session and stopped, leaving the lists on a skeleton until the operator reloaded by hand.
- A form key containing a colon (`teamMember:<id>`) collided with the `"<key>:<value>"` encoding the DOM uses for a form value, so the team-member select silently stored the wrong thing under the wrong name. Both key builders now live in one place and are asserted to contain no separator.
- `PATCH /tenants/{id}/teams/{id}` required the team's name in order to archive it, which is how a team gets renamed by accident; and restoring a team whose name had since been reused produced a **500**. The patch is now genuinely partial, and the partial unique index's refusal is translated into the same `409 team_exists` the create path gives, by a shared helper that rethrows every other failure untouched.

Two read models grew for the same reason. `GET /tenants/{id}/teams` now returns each team's `members` and its `archived` flag: a card that said "3 members" and offered no way to see or remove them left `removeTeamMember` reachable only from a hand-written request. The custom-role editor now offers exactly the **delegable** keys from `GET /tenants/{id}/permissions` instead of four hard-coded strings, and is disabled until a key and a scope have actually been chosen — a convenience, not the control, since `canAuthorRole` still refuses on the server.

The dev server proxies `/api` to the running API (`apps/web/vite.config.ts`), so the browser uses the same same-origin path in development and in a deployed build; there is no second base URL that exists only locally, and with it no class of CORS and cookie bugs that never appear in production.

**P1-T7 / Milestone C, first slice (2026-09-09)** built the channel foundation and the first complete inbound path: connect an asset → the provider delivers a signed webhook → the company is resolved from the asset → the raw event is journaled → a normalized inbound event exists. Every step is proved against real PostgreSQL under FORCE RLS.

Three decisions shape migration `0010_channels.sql`.

**A secret never sits in an ordinary column.** An app secret belongs to the installation, so `channel_apps` stores a *reference* to the configuration key it is read from plus a fingerprint of the value it was created against — rotating it is an operations act, and a database reader learns nothing. A tenant's access token cannot live in configuration because it arrives from an OAuth grant, so it is AES-256-GCM ciphertext with the tenant, connection and purpose as additional authenticated data: a ciphertext lifted into another row does not decrypt, it breaks. That is asserted three ways, along with a fresh IV per record so two companies storing the same token are not visibly storing the same token.

**The company is resolved from a verified asset, never from the caller.** A webhook has no session. `channel_asset_registry` maps a provider asset to its owner installation-wide, and its RLS policy admits exactly the row whose fingerprint the ingress derived from a signature-verified payload — the same one-row carve-out invitations use, under its own transaction setting (`convo.asset_fingerprint`) so a bug in either cannot widen the other. `withCredentialResolvedTenant` now takes the setting as a parameter rather than hard-coding one.

**What we received and what was in it are different facts.** `webhook_receipts` is installation-level evidence that bytes arrived and whether their signature held, and carries no payload. The payload lives in a tenant-scoped `channel_events` row and only for a delivery we could route. A signature-valid delivery for an asset nobody here has connected leaves a receipt, no content and a 202 — retrying it forever helps nobody, and storing a stranger's customer messages would be worse than dropping them.

**"Connected" is earned, not declared.** Submitting the connect form produces a connection in `authorization_needed` with four missing pieces of evidence. Only `POST .../test` may record that a provider accepted a credential; only the ingress may record that a webhook arrived. `readinessOf` derives the state in one pure function that the stored column and the screen share, so no endpoint can write `healthy`.

The domain owns the pure half — five capability matrices, the send policy, Meta signature verification, WhatsApp normalization — and it is exhaustively tested. A WhatsApp template cannot be accepted for Messenger or Instagram because those matrices have no template concept at all. Text limits are enforced in characters **and** UTF-8 bytes, which is the difference between 1000 and 500 for Arabic (CH-IG-04).

**There is no provider simulator, deliberately.** A simulator that answered "accepted" would make the screen show a working channel — a lie told by our own code rather than by a provider. The default transport refuses every send and every connection test with `provider_not_connected`. One integration suite binds a clearly-labelled stub to exercise our own success and failure handling; it produces no message id and is bound nowhere in the shipped composition root.

Two gates stopped being placeholders. `test:contracts` and `test:security` were `exit 1` echoes; they now run the adapter and OpenAPI contract suites and the isolation/authorization/signature suites plus a production dependency audit. Wiring the audit immediately found **9 high and 1 critical** advisories in the HTTP stack — middleware and authentication bypasses in `@fastify/middie`, `fastify` and `@nestjs/platform-fastify` — so those dependencies were upgraded. Two moderate advisories remain, below the gate.

**P1-T7 / Milestone C, second slice (2026-09-09)** wired the Channels screen to those endpoints and deleted the demo one, along with the `channel` demo action that answered four verbs with a warning toast.

The screen exists to say one thing clearly: a channel is not connected because somebody pasted a token. Each connection lists the five separate pieces of evidence and which are still missing, so `webhook_pending` reads as "waiting for the provider to deliver something" rather than as an amber light. The token is dropped from form state whether the connect succeeds or is refused — a credential left in a form field is a credential in a screenshot — while the other fields survive a refusal so the attempt can be corrected. Inputs whose value gates a control dispatch `form-toggle` rather than `form`, because a disabled state one keystroke behind is a control that looks broken.

**The visual gate was found to be broken, and fixed.** Replacing the Channels screen wholesale — four cards of demo data becoming one state box — passed `toHaveScreenshot` at `maxDiffPixelRatio: 0.02`. Measured: Arabic glyph rasterisation varies run to run by about 1.4% of a text-dense screen, and the replacement moved about 2%, because most of both screens is near-white on near-white and only glyph pixels ever exceed the per-pixel threshold. Those two numbers cannot be separated by a ratio. **P1-T7 / Milestone C, third slice (2026-09-09)** built the outbound path: a command, a durable outbox, an attempt ledger, and two delivery state machines that fold independently.

Every column in migration `0011_outbound.sql` exists because the obvious simpler design is wrong in a specific way.

**`outcome_unknown` is a state, not an error.** Between sending a request and storing the answer there is a window in which we genuinely cannot know whether a message went out. The industry default — retry on timeout — sends duplicate messages to real customers. It gets its own command state, it leaves the outbox, and nothing automatic touches it again. The test counts transport calls across a second dispatch sweep *and* a recovery sweep and asserts the number did not move.

**Command state and delivery state are different columns.** Nine states for what we asked the provider to do, three for what the provider later says happened, folded by two different functions. There is no ordering over the command states and no `max()` anywhere. `foldDelivery` never moves the delivery state backwards and records `delivered_after_read` as an anomaly rather than discarding the disagreement — asserted over every permutation of three receipts, and end to end with a real out-of-order pair of webhooks.

**The attempt row commits before the network call.** After a crash, recovery finds an attempt with no recorded response and marks it `outcome_unknown` — it does not resend. This is asserted by holding the stub transport open and observing the attempt mid-flight with a null outcome: an attempt table written *after* the response cannot tell "never sent" from "sent, answer lost".

**The permit is re-evaluated at dispatch, not at draft.** A window that was open when an agent typed can be shut by the time a worker picks the message up; consent can be withdrawn; the channel can be disconnected; the credential can be revoked. Each of those four has a failing-path test, and each produces `skipped` with a typed reason rather than a send.

**One conversation puts one message on the wire at a time.** `DISTINCT ON` within a batch, `NOT EXISTS` against committed leases, `pg_try_advisory_xact_lock` for the gap between them where a concurrent claim has not committed yet, and a partial unique index as the durable last line. Two messages queued for one recipient are claimed one sweep at a time.

**A receipt that arrives before the send response is not lost.** It is an ordinary inbound event whose message is not yet identifiable; the moment the provider id is learned, held receipts for it are folded in.

The stub transport in the integration tests is a **stub, not a simulator of a provider**: it exists so our own handling of accepted, rejected and unknown outcomes can be exercised at all, and it is bound nowhere outside that file. **P1-T7 / Milestone C, fifth slice (2026-09-09)** closed the rest of Milestone C: separate process roles, the durable broker relay, the fair scheduler, `dispatch_version` fencing, and realtime with authorized, projected events.

**One artifact, seven roles.** `CONVO_PROCESS_ROLE` alone decides what a process is. HTTP roles listen; the four worker roles run a loop and bind no port — asserted by starting one and reading `null` from the server's address. `worker-integration` fails closed when no durable broker is reachable, because a process whose only job is publishing has nothing to do without one; nothing silently becomes an in-memory queue. A tick that throws backs off rather than killing the loop, and `SIGTERM` stops it between ticks so a lease is never severed mid-write.

**The broker is a transport, and the outbox is the source of truth (ADR-0004).** An envelope is written in the same transaction as the effect and published afterwards; `published_at` is set only on a confirmation. That ordering means a publish can happen twice, which is accepted rather than papered over: `broker_deliveries` makes every consumer idempotent, so a duplicate is absorbed and a lost event would not be. Retries are bounded at eight; the ninth quarantines the envelope with its reason. A replay creates a new envelope and records who did it.

**Fencing is enforced, not just recorded.** `claim()` returns the version the worker owns, and every result write compares it. A worker whose lease expired writes nothing to the command — but its attempt row is written **first and unconditionally**, because a stale worker's provider response is still evidence about what a customer may have received. It is marked `stale_dispatch` so the evidence is never mistaken for current state. Four stale paths are tested: accept, `outcome_unknown`, rejection and retry.

**The round is bounded and dealt.** `planRound` serves interactive first up to the whole capacity and gives bulk the remainder, and within a class it deals one slot at a time so a company offering ten thousand messages cannot push a company offering one to the back. Before this, every pending company got up to `concurrency` messages per tick, so a tick's size depended on how many companies happened to be busy — a queue with no ceiling. The worker now reports `offered` beside `achieved`, because `handled` alone reads the same whether a round served everything or a tenth of it.

**Realtime is authorization, not transport.** Every event is decided again on the way out, by the *same* `authorize` the HTTP routes use, against a principal re-read from the database — so revoking a role, suspending a membership or removing an inbox stops the stream on the next poll rather than at the next login.
