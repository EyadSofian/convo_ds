# تقرير فحص التسليم والإنتاج — DS Omnichannel

التاريخ: 17 أكتوبر 2026 (توقيت القاهرة)  
الهدف: مقارنة كود GitHub مع النسخة الحية على Railway، وتشغيل الاختبارات الآمنة المتاحة، وحصر العيوب والفجوات المثبتة.  
القرار الحالي: **أُصلحت عيوب الكود والاختبارات المكتشفة محليًا؛ النسخة الحية لا تزال إصدارًا أقدم، ولا يجوز اعتبار إصلاحاتها منشورة قبل ترقية Railway والتحقق منها.**

**فجوة إعداد إنتاجية إضافية:** فحص أسماء متغيرات Railway فقط (دون قراءة قيم الأسرار) لم يُظهر `CONVO_CHANNEL_TRANSPORT` على API وعمّال قنوات الإنتاج. لذلك لا يمكن الادعاء بأن ترقية الكود وحدها ستُفعّل مراسلة Meta؛ يلزم اعتماد إعدادات الإنتاج الصحيحة والتحقق من مسار webhook والإرسال والاستقبال. لا تُنسخ أسرار staging إلى production تلقائيًا.

**بوابات الكود الجديد محليًا:** lint وTypeScript والبناء ناجحة؛ Vitest ‏٣٢٤١/٣٢٤١ مع تغطية ١٠٠٪ للسطور والفروع والدوال والتعليمات؛ Playwright ‏٥٠٤/٥٠٤؛ وفحص الاعتماديات الإنتاجية دون ثغرات معروفة. هذه نتائج الكود المحلي، وليست إثباتًا لتشغيل خدمات الإنتاج.

الأقسام التالية تحفظ لقطة الفحص الأصلي قبل الإصلاح للمقارنة؛ جدول «تحديث المعالجة» أعلاه هو الحالة الأحدث.

## 5. ما لا يمكن اعتبارُه مُختبَرًا بالكامل

- دخول مستخدم إنتاجي، صلاحياته، واجهة الحساب، CRUD للجهات والملصقات، الاستيراد والتصدير على بيانات إنتاجية؛ لم تتوفر جلسة اختبار مخصصة خالية من بيانات العملاء.
- إرسال/استقبال Meta WhatsApp وMessenger/Instagram، webhook موقّع، قراءة الرسائل، قوالب، حملات، push على هاتف حقيقي، وبريد فعلي. اختبارات المحاكاة لا تثبت نجاح المزود الحقيقي.
- حالة وصحة جميع العمال من داخل الشبكة الخاصة، مسارات alerting، PITR، واستعادة backup إنتاجي إلى هدف معزول.
- اختبارات حمل أو فوضى على الإنتاج. تشغيلها قد يؤثر على العملاء، ولم يُؤذَن بتغيير بياناتهم أو تعطيل الخدمة.
- حصر «كل الأخطاء» حرفيًا غير ممكن دون هذه البوابات؛ هذا التقرير يحصر **ما ثَبَت** ويذكر ما بقي غير مثبت بوضوح.

## 6. تسلسل الإغلاق المقترح قبل التسليم

1. إصلاح F-03 (OpenAPI/route contract) وتشغيل CI على `main` حتى يصبح أخضر.
2. مراجعة الاعتماديات في F-02/F-04 وإعادة audit، ثم اعتماد إصدار Git SHA ثابت واختباره على staging.
3. معالجة اختلافات الصور المرجعية في اختبارات `main` بعد التأكد من التصميم المقصود، وعدم قبول صور جديدة لمجرد إسكات الاختبار.
4. التحقق من ترقية Railway المقصودة دون نسخ staging إلى production أو تشغيل migration غير مراجع؛ ثم مقارنة كل deployment ID وSHA.
5. تهيئة حساب اختبار إنتاجي/مزوّدات اختبار مصرح بها وتنفيذ رحلة end-to-end حقيقية، ثم backup/restore معزول وقياس حمل على staging مماثل للإنتاج. توثيق هذه النتائج في تقرير محدث.
